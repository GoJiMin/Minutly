# Minutly PRD

## 1. 프로젝트 개요

### 1-1. 서비스명

- **Minutly**
- 회의 중 오간 대화를 텍스트로 전환하고, 이를 기반으로 회의 내용을 정리해주는 웹 서비스

### 1-2. 문제 정의

노트북을 들고 회의실에 들어가는 사용자는 회의 중 메모에 집중하면 대화를 놓치기 쉽고, 대화에 집중하면 회의 내용을 정리하는 데 추가 시간이 든다.

특히 회의가 끝난 뒤에는 다음과 같은 불편이 반복된다.

- 회의 내용을 다시 기억에 의존해 정리해야 한다.
- 주요 논의 사항과 결정 사항을 따로 분류해야 한다.
- 회의 직후 빠르게 공유할 수 있는 형태의 결과물이 없다.

Minutly는 회의 중 마이크로 입력된 음성을 텍스트화하고, 회의 요약 결과를 제공함으로써 이 문제를 해결한다.

### 1-3. 목표

- 사용자가 회의 중 별도 메모 없이 대화에 집중할 수 있도록 한다.
- 회의 종료 직후 바로 활용 가능한 정리 결과를 제공한다.
- 최소 기능만으로 빠르게 PoC를 검증한다.

## 2. 타겟 사용자

### 2-1. 핵심 타겟

- 노트북을 들고 회의에 참여하는 사용자
- 회의록 작성을 번거롭게 느끼는 사용자
- 회의 직후 논의 내용을 빠르게 정리해야 하는 사용자

### 2-2. 초기 사용자

- 월 회의 시간이 5시간 이내인 1인 사용자
- 개인적으로 회의 내용을 정리하고 공유할 필요가 있는 사용자

---

## 3. 제품 목표

### 3-1. 핵심 가치

- **기록 자동화**: 회의 중 대화를 텍스트로 수집한다.
- **정리 자동화**: 수집된 텍스트를 회의 결과물 형태로 정리한다.
- **즉시성**: 회의 종료 후 바로 읽을 수 있는 결과를 제공한다.

### 3-2. PoC 목표

- 웹에서 마이크 입력을 받아 회의 내용을 텍스트화할 수 있다.
- 텍스트를 기반으로 회의 요약 결과를 생성할 수 있다.
- 친구 1명이 실제 회의에서 무리 없이 사용할 수 있다.

## 4. 핵심 기능 범위

### 4-1. 포함 범위 (In Scope)

1. 사용자가 웹에서 녹음을 시작할 수 있다.
2. 회의 중 마이크 입력을 텍스트로 변환할 수 있다.
3. 누적된 텍스트로 AI 요약을 요청할 수 있다.
4. 회의 종료 후 다음과 내용이 포함된 결과를 보여줄 수 있다.
   - 총 회의 요약
   - 주요 사항
5. 결과를 화면에서 읽을 수 있다.
6. 회의 결과를 날짜 기준으로 저장할 수 있다.
7. 사용자는 저장된 회의 목록을 날짜별로 확인할 수 있다.
8. 사용자는 저장된 회의 상세 내용을 다시 확인할 수 있다.
9. 사용자는 저장된 회의를 삭제할 수 있다.
10. 사용자는 저장된 회의의 제목, 회의 요약, 주요 사항을 수정할 수 있다.

### 4-2. 제외 범위 (Out of Scope)

- 회의방 생성 및 초대 기능
- 다중 사용자 협업
- 계정 시스템
- 파일 업로드를 통한 음성 인식
- 실시간 공동 편집
- 고도화된 권한 관리
- SEO 최적화

## 5. 핵심 사용자 시나리오

### 5-1. 기본 시나리오

1. 사용자가 Minutly에 접속한다.
2. 사용자가 `녹음 시작` 버튼을 클릭한다.
3. 브라우저가 마이크 권한을 요청한다.
4. 회의 중 입력된 음성이 텍스트로 변환된다.
5. 사용자가 `녹음 종료` 버튼을 클릭한다.
6. 서비스가 전사된 원문 텍스트를 먼저 보여준다.
7. 사용자는 AI 요약 전에 전사 텍스트의 오타를 검토하고 수정할 수 있다.
8. 수정된 텍스트로 AI 요약을 요청한다.
9. 서비스가 회의 요약과 주요 사항을 보여준다.
10. 필요 시 사용자는 저장된 회의의 제목, 회의 요약, 주요 사항을 수정할 수 있다.

### 5-2. 성공 조건

- 사용자는 별도 메모 없이 회의에 참여할 수 있다.
- 회의 종료 후 핵심 내용을 빠르게 확인할 수 있다.
- 사용자는 저장된 회의를 삭제하거나 제목, 회의 요약, 주요 사항을 수정할 수 있다.

## 6. 기능 요구사항

### 6-1. 녹음 및 전사

- 사용자는 녹음을 시작/종료할 수 있어야 한다.
- 마이크 권한 상태를 인지할 수 있어야 한다.
- 회의 중 음성 입력은 텍스트로 누적되어야 한다.
- 한국어를 기본 지원해야 한다.
- 영어 회의도 인식 가능하면 좋다.
- 녹음 중 화면에는 실시간 전사 전체가 아니라 최근 전사 미리보기만 보여준다.
- 실시간 전사 미리보기는 최종 인식이 완료된 문장 기준 최근 10개 문장만 표시한다.
- 녹음 종료 후 전사 원문 전체를 사용자에게 보여줄 수 있어야 한다.
- 사용자는 전사 원문을 직접 수정할 수 있어야 한다.

### 6-2. 요약 결과

- 전사된 텍스트를 요약 AI에 전달할 수 있어야 한다.
- 요약은 사용자가 최종 확인한 텍스트를 기준으로 생성되어야 한다.
- 결과는 다음 두 섹션으로 고정한다.
  - 총 회의 요약
  - 주요 사항
- 요약 생성 전 전사 텍스트가 수정되면 수정한 텍스트로 요약을 생성한다.

### 6-3. 회의 히스토리

- 회의 종료 후 전사 원문과 요약 결과를 함께 저장할 수 있어야 한다.
- 저장된 회의는 날짜별로 목록화되어야 한다.
- 사용자는 특정 회의를 선택해 상세 내용을 다시 볼 수 있어야 한다.
- 사용자는 저장된 회의를 삭제할 수 있어야 한다.
- 사용자는 저장된 회의의 제목을 수정할 수 있어야 한다.
- 사용자는 저장된 회의의 총 회의 요약을 수정할 수 있어야 한다.
- 사용자는 저장된 회의의 주요 사항을 수정, 추가, 삭제할 수 있어야 한다.
- 저장된 회의의 원문은 읽기 전용이어야 한다.
- 저장 단위는 회의 1건 단위여야 한다.

### 6-4. 사용자 경험

- 인터페이스는 단순해야 한다.
- 사용자는 현재 상태를 명확히 알 수 있어야 한다.
  - 대기 중
  - 녹음 중
  - 오류 발생
  - 요약 생성 중
  - 완료
- 결과는 읽기 쉬운 형태로 제공되어야 한다.
- 녹음 중 중단 이력이 있는 경우 사용자는 이를 인지할 수 있어야 한다.
- 요약 전 원문 검토 단계에서 사용자는 누락 가능 구간을 보완할 수 있어야 한다.
- 원문에는 중단된 지점을 식별할 수 있도록 `[녹음 중단 구간]` 표시를 삽입할 수 있어야 한다.
- 저장된 회의를 삭제하거나 원문을 다시 수정하는 기능이 복잡하지 않아야 한다.

## 7. 비기능 요구사항

### 7-1. 비용

- PoC 단계에서 별도 비용이 들지 않아야 한다.
- STT는 무료 사용량 안에서 운영 가능해야 한다.
- 저장소 역시 무료 범위 안에서 운영 가능해야 한다.

### 7-2. 기술 제약

- 웹 기반 서비스로 제공한다.
- SEO는 중요하지 않다.
- 초기 버전은 1인 사용에 최적화한다.
- 애플리케이션은 Vercel에 배포한다.
- 최종 회의 기록은 Neon Postgres를 영속 저장소로 사용한다.

### 7-3. 품질 기준

- 회의 시작/종료 플로우가 단순하고 안정적이어야 한다.
- 전사 결과가 지나치게 자주 유실되지 않아야 한다.
- 짧은 회의에서도 자연스럽게 동작해야 한다.

## 8. 기술 방향 초안

### 8-1. 애플리케이션 구조

- Next.js 기반 웹 애플리케이션
- 단일 사용자 중심의 단순 UI
- 서버와 클라이언트를 하나의 프로젝트에서 함께 관리

### 8-2. 음성 인식

- Azure Speech F0 Free Tier 사용
- 월 5시간 무료 사용량 내에서 PoC 운영
- 한국어를 기본으로 지원하고, 필요 시 영어까지 대응
- 실시간 화면 표시는 Azure STT의 최종 인식 완료 이벤트 기준으로 갱신한다.
- 녹음 중 미리보기는 최근 10개 문장만 유지해 화면 렌더링 범위를 제한한다.

### 8-3. 저장 방식

- 최종 회의 데이터는 Neon Postgres에 저장한다.
- 회의 1건은 데이터베이스의 회의 레코드 1개로 관리한다.
- 날짜별 목록과 캘린더 표시는 `meetingDate` 기준으로 조회한다.
- 저장 데이터는 최소 스키마를 유지해 단순하게 관리한다.
- 녹음 중이거나 아직 최종 저장되지 않은 데이터는 브라우저 `localStorage`에 임시 저장한다.

#### DB 저장 구조

- 최종 회의 데이터는 `meetings` 테이블에 저장한다.
- 각 회의는 고유한 `id`를 가진다.
- `id`는 날짜나 시간 문자열에 의존하지 않는 데이터베이스 레코드 식별자로 사용한다.
- `meetingDate`는 `createdAt`을 서비스 기준 시간대인 `Asia/Seoul`로 해석해 생성한 날짜다.
- 회의 날짜 그룹은 `meetingDate`를 기준으로 판단한다.
- 월별 캘린더 조회는 조회 대상 월의 시작일 이상, 다음 달 시작일 미만의 `meetingDate` 범위 조회로 처리한다.
- 하루에 여러 회의가 있어도 각 회의는 고유한 `id`로 구분한다.
- 같은 날짜의 회의 목록은 생성 시각 오름차순으로 정렬한다.

#### 임시 저장 규칙

- 녹음 중 원문 초안은 1분 단위로 `localStorage`에 자동 저장한다.
- 사용자가 `녹음 종료`를 눌렀을 때도 최신 원문을 한 번 더 임시 저장한다.
- 녹음 중 오류가 발생하면 현재까지의 원문을 즉시 한 번 더 임시 저장한다.
- 임시 저장 데이터는 회의 중 예기치 않은 오류, 수동 재녹음, 새로고침 상황에서 복구 용도로 사용한다.
- AI 요약이 완료되고 Neon Postgres 최종 저장까지 성공하면 해당 임시 저장 데이터는 제거한다.
- 요약 실패 또는 저장 실패 시 임시 저장 데이터는 유지한다.

#### DB 저장 스키마 초안

- `id`: 각 회의를 구분하는 고유 식별자
- `title`: 회의 제목
- `meetingDate`: 캘린더 및 날짜별 목록 조회에 사용하는 서비스 기준 날짜
- `createdAt`: 회의 생성 시각
- `updatedAt`: 마지막 수정 시각
- `originTranscript`: STT가 인식한 원본 텍스트
- `transcript`: 사용자가 검토 및 수정한 최종 텍스트
- `summary`: AI가 생성하고 사용자가 수정할 수 있는 총 회의 요약
- `keyPoints`: AI가 생성하고 사용자가 수정할 수 있는 주요 사항 목록

#### 저장 규칙

- 회의가 처음 생성될 때 `createdAt`과 `updatedAt`은 같은 값으로 저장한다.
- `meetingDate`는 최초 저장 시 생성하며, 저장된 회의 수정 시에는 유지한다.
- 제목, 총 회의 요약, 주요 사항이 변경되면 `updatedAt`을 갱신한다.
- 신규 회의 저장은 새 레코드 생성으로 처리한다.
- 저장된 회의 수정은 기존 레코드 갱신으로 처리한다.

#### 저장 데이터 예시

```json
{
  "id": "9d8c0b40-66b4-4e19-a8a2-69d7b4d4b3c2",
  "title": "[2026-04-26. 일] - 메디큐브 시딩 제품 관련 오션 회의",
  "meetingDate": "2026-04-26",
  "createdAt": "2026-04-26T14:00:00+09:00",
  "updatedAt": "2026-04-26T14:18:32+09:00",
  "originTranscript": "회의 원문 전사 텍스트",
  "transcript": "사용자가 수정한 최종 회의 텍스트",
  "summary": "회의 요약문",
  "keyPoints": [
    "시딩 제품 마케팅 방향 재검토",
    "오션 측 피드백을 반영한 상세 페이지 문구 수정 필요",
    "다음 주까지 샘플 배포 일정 확정 필요"
  ]
}
```

### 8-4. 배포 방향

- Vercel 배포를 기본 배포 방식으로 사용한다.
- Git 배포를 우선 사용한다.
- 영속 데이터 저장은 Neon Postgres 연결을 통해 처리한다.
- API 키, 인증 로그인 정보, 데이터베이스 연결 정보는 Vercel 환경 변수로 관리한다.

### 8-5. 인증

- 초기 버전은 1인 사용을 전제로 단일 로그인 정보(`id`/`password`) 보호 방식을 검토
- 인증 정보는 서버 환경 변수로 관리하고, 서버에서만 검증
- 인증 토큰은 `httpOnly` 쿠키 기반 access token과 refresh token으로 관리
- 보호된 API는 access token을 기준으로 검증하고, refresh token 쿠키가 있어 갱신 시도가 가능한 경우에만 `TOKEN_EXPIRED`를 반환
- 로그인 실패, refresh token 검증 실패 등 갱신할 수 없는 인증 실패는 구체적인 실패 원인을 노출하지 않음

### 8-6. 요약

- 전사 결과를 별도 AI 요약 모델에 전달
- 요약 모델 자체는 본 프로젝트 범위에서 자유롭게 교체 가능

## 9. MVP 화면 구성 초안

### 9-1. 메인 화면

- 서비스 소개 문구
- 녹음 시작 버튼
- 현재 상태 표시
- 최근 10개 문장을 보여주는 실시간 전사 미리보기 영역
- 최근 회의 목록 또는 히스토리 화면 진입 영역

### 9-2. 결과 화면

- 총 회의 요약
- 주요 사항
- 원문 전사 텍스트
- 회의록 편집 버튼
- 회의 삭제 버튼

### 9-3. 히스토리 화면

- 화면의 1/3을 좌측 영역, 2/3을 우측 영역으로 분리
- 좌측 영역 상단에 캘린더 표시
  - 회의가 존재하는 날짜 강조 표시
  - 사용자가 날짜를 선택할 수 있는 인터랙션 제공
- 좌측 영역 하단에 선택한 날짜의 회의 목록 표시
  - 같은 날짜의 회의는 생성 시각 오름차순으로 정렬
- 우측 영역에 선택한 회의의 상세 내용 표시

## 10. 상태 전이 초안

### 10-1. 주요 상태

- `idle`: 아직 녹음을 시작하지 않은 초기 상태
- `recording`: 사용자가 회의 내용을 녹음 중인 상태
- `transcript_review`: 녹음 종료 후 전사 원문을 검토 및 수정하는 상태
- `summarizing`: 수정된 전사 텍스트로 AI 요약을 생성 중인 상태
- `completed`: 요약 결과 생성이 완료되어 회의 내용을 확인할 수 있는 상태
- `error`: 녹음, 전사, 요약, 저장, 삭제 중 하나라도 실패가 발생해 사용자 조치가 필요한 상태

### 10-2. 상태 전이 규칙

- 사용자가 `녹음 시작`을 누르면 `idle`에서 `recording`으로 전이된다.
- 녹음 중 STT 오류나 연결 오류가 발생하면 현재 원문을 임시 저장한 뒤 `recording`에서 `error`로 전이된다.
- 사용자가 오류 상태에서 `다시 녹음 시작`을 누르면 기존 원문 유지한 채 `error`에서 `recording`으로 전이된다.
- 다시 녹음을 시작할 때는 원문에 `[녹음 중단 구간]` 표시를 삽입한 뒤 이후 전사를 이어서 누적한다.
- 사용자가 `녹음 종료`를 누르면 `recording`에서 `transcript_review`로 전이된다.
- 사용자가 `요약 생성`을 누르면 `transcript_review`에서 `summarizing`으로 전이된다.
- 요약 생성이 성공하면 `summarizing`에서 `completed`로 전이된다.
- 저장된 결과에서 제목, 회의 요약, 주요 사항을 수정할 수 있다.
- 요약, 저장, 인증 등 사용자 재시도가 필요한 오류가 발생하면 각 상태에서 `error`로 전이될 수 있다.

### 10-3. 상태별 사용자 액션

- `idle`: 녹음 시작 가능
- `recording`: 녹음 종료 가능
- `transcript_review`: 원문 수정 및 요약 생성 가능
- `summarizing`: 대기 상태, 중복 요청 방지
- `completed`: 결과 확인, 제목 수정, 회의 요약 수정, 주요 사항 수정/추가/삭제, 삭제 가능
- `error`: 오류 메시지 확인, 다시 녹음 시작, 재시도 가능

## 11. 저장 시점 규칙 초안

### 11-1. 기본 원칙

- 저장은 임시 저장과 최종 저장으로 나누어 관리한다.
- 임시 저장은 회의 중 데이터 유실 방지를 위한 안전장치로 사용한다.
- 최종 저장은 사용자가 검토한 결과를 기준으로 수행한다.

### 11-2. 저장 시점

- 녹음 중에는 원문 초안을 1분 단위로 `localStorage`에 임시 저장한다.
- 사용자가 `녹음 종료`를 누른 시점에도 최신 원문을 한 번 더 임시 저장한다.
- 녹음 중 오류가 발생하면 현재 원문을 즉시 임시 저장한다.
- 녹음 종료 직후에는 최종 DB 저장을 수행하지 않는다.
- 사용자가 원문을 검토 및 수정하고 제목을 입력한 뒤 요약 생성이 완료되면 최초 DB 저장을 수행한다.
- 저장된 회의의 제목, 총 회의 요약, 주요사항을 수정하면 같은 회의 레코드를 갱신한다.
- 회의 데이터의 제목, 총 회의 요약, 주요사항이 변경되면 같은 회의 레코드를 갱신한다.
- DB 저장이 성공하면 관련 임시 저장 데이터는 제거한다.
- 저장 시 `updatedAt`을 함께 갱신한다.

### 11-3. 저장 단위

- 회의 1건당 DB 레코드 1개를 저장한다.
- 최종 저장 대상은 회의 데이터 전체다.
- 부분 필드만 따로 저장하지 않고, 하나의 완성된 회의 데이터 단위로 관리한다.
- 임시 저장은 최종 DB 데이터와 별도로 원문 중심의 임시(draft) 데이터만 관리한다.

## 12. 제목 입력 규칙 초안

### 12-1. 기본 원칙

- 제목은 사용자가 회의를 식별할 수 있을 정도로 충분히 구체적이어야 한다.
- 제목의 핵심 내용은 사용자가 직접 입력한다.
- 시스템은 `meetingDate`를 기준으로 날짜와 요일 prefix를 자동으로 붙인다.
- 사용자는 저장 전과 저장 후 모두 제목을 수정할 수 있어야 한다.

### 12-2. 제목 구성 규칙

- 제목 형식은 기본적으로 `[YYYY-MM-DD. 요일] - 사용자 입력 제목`으로 구성한다.
- 날짜와 요일은 `meetingDate`를 기준으로 자동 생성한다.
- 사용자 입력값은 날짜 prefix 뒤에 이어 붙인다.
- 예시: `[2026-04-26. 일] - 메디큐브 시딩 제품 관련 오션 회의`

### 12-3. 입력 규칙

- 사용자는 제목 입력란에 날짜를 제외한 회의 이름만 입력한다.
- 제목이 비어 있으면 저장할 수 없도록 한다.
- 제목 수정 시 `updatedAt`을 함께 갱신한다.

## 13. 에러 및 예외 처리 초안

### 13-1. 주요 에러 상황

- 사용자가 마이크 권한을 거부한 경우
- 마이크 장치를 찾지 못한 경우
- STT 전사 도중 연결 또는 서비스 오류가 발생한 경우
- 녹음이 회의 중간에 예기치 않게 중단된 경우
- 원문이 비어 있거나 지나치게 짧은 경우
- AI 요약 생성에 실패한 경우
- DB 저장에 실패한 경우
- 회의 삭제에 실패한 경우
- 인증에 실패한 경우

### 13-2. 처리 원칙

- 에러 발생 시 사용자가 현재 어떤 문제가 발생했는지 이해할 수 있어야 한다.
- 전사 결과와 입력 데이터는 가능한 한 유지해 재시도를 지원해야 한다.
- 녹음 중 오류가 발생하면 현재 원문을 즉시 임시 저장하고, 사용자에게 중단 사실을 명확히 안내해야 한다.
- 사용자는 오류 상태에서 직접 다시 녹음을 시작할 수 있어야 한다.
- 다시 녹음을 시작할 때는 기존 원문을 유지한 채 이어서 기록해야 한다.
- 녹음 중 오류가 발생해도 마지막 임시 저장 시점까지의 원문은 복구 가능해야 한다.
- 중단 이력이 있는 회의는 요약 전에 사용자가 누락 가능 구간을 검토할 수 있어야 한다.
- 원문에는 `[녹음 중단 구간]` 표시를 삽입해 사용자가 중단 지점을 쉽게 식별할 수 있어야 한다.
- 실시간 화면 표시용 데이터는 최근 10개 문장만 유지해 렌더링 부담을 제한해야 한다.
- 요약 실패 시 원문은 유지하고, 요약 생성을 다시 시도할 수 있어야 한다.
- 저장 실패 시 DB 저장은 실패하더라도 임시 저장 데이터는 유지해 재시도를 지원해야 한다.

### 13-3. 사용자 안내 예시

- 마이크 권한 거부: 브라우저 권한을 허용해달라는 안내 제공
- 녹음 중단: `녹음이 중단되었습니다. 다시 녹음을 시작해주세요.`와 같은 안내 제공
- 수동 재녹음: `다시 녹음 시작` 버튼 제공
- 중단 이력 존재: `중간에 일부 누락된 내용이 있을 수 있으니 요약 전에 확인해주세요.`와 같은 안내 제공
- 요약 실패: 원문은 유지한 채 `요약 생성` 버튼 제공
- 저장 실패: 다시 저장 시도 가능하도록 안내
- 삭제 실패: 다시 삭제를 시도할 수 있도록 안내

## 14. 히스토리 UX 규칙 초안

### 14-1. 목록 규칙

- 히스토리 화면은 캘린더 기반으로 회의를 탐색할 수 있어야 한다.
- 회의가 존재하는 날짜는 캘린더에서 강조 표시되어야 한다.
- 사용자가 특정 날짜를 선택하면 해당 날짜의 회의 목록을 확인할 수 있어야 한다.
- 같은 날짜에 여러 회의가 있을 경우 목록은 생성 시각 오름차순으로 정렬한다.
- 목록에는 회의 제목을 보여준다.

### 14-2. 그룹 기준

- 히스토리의 1차 그룹 기준은 `meetingDate`다.
- 캘린더의 날짜 셀은 `meetingDate` 기준으로 회의 존재 여부를 판단한다.
- 같은 날짜의 회의는 해당 날짜 그룹 안에서만 정렬한다.

### 14-3. 상세 화면 규칙

- 히스토리 화면은 좌측 캘린더, 우측 상세 영역의 2분할 화면을 사용한다.
- 우측 상세 영역은 선택한 날짜의 회의 목록과 선택한 회의의 상세 내용을 함께 보여줄 수 있어야 한다.
- 상세 화면에서는 제목, 생성 시각, 최종 수정 시각을 보여준다.
- 원문과 총 회의 요약은 구분된 영역으로 보여준다.
- 주요사항은 별도의 목록 형태로 강조해 보여준다.
- 상세 화면에서는 제목, 총 회의 요약, 주요 사항 편집과 회의 삭제 기능을 제공할 수 있어야 한다.

## 15. 개인정보 및 보안 정책 초안

### 15-1. 저장 데이터 범위

- 오디오 원본 파일은 저장하지 않는다.
- 저장 대상은 원문, 총 회의 요약, 주요사항, 제목, 생성 시각 등 텍스트 기반 데이터만 포함한다.

### 15-2. 접근 제어

- 초기 버전은 1인 사용을 전제로 단일 로그인 정보(`id`/`password`) 보호 방식을 사용한다.
- `id`와 `password`는 서버 환경 변수로 관리한다.
- 로그인 정보 검증은 서버에서만 수행한다.

### 15-3. 보안 원칙

- 클라이언트에 민감한 인증 정보를 노출하지 않는다.
- 회의 데이터는 Neon Postgres에 저장되며, 외부에 공개되지 않아야 한다.
- 로그에는 민감한 회의 내용이 과도하게 남지 않도록 주의한다.

## 16. 성공 지표

- 실제 회의 녹음부터 요약 결과를 확인할 수 있다.
- 사용자 1명이 월 무료 사용량 범위 내에서 서비스를 사용할 수 있다.
- 결과물이 직접 수기 정리한 메모를 일부 대체할 수 있다고 느낀다.
